### Condition décisive : interne ou post-FX

Le fournisseur RTC reste BytePlus dans les deux modes. C'est **la source audio** qui change :

- `internal` : micro capturé directement par BytePlus ; la console de performance n'est pas sa source publique.
- `external` : capture et DSP gérés par l'application ; le bus post-FX devient la source publique BytePlus.

`PlaceBytePlusAudioTransportPreference.current` lit d'abord `MEEWAV_BYTEPLUS_AUDIO_TRANSPORT`, puis `MEEWAVBytePlusAudioTransport` dans l'Info.plist. Les configurations Xcode versionnées ont `MEEWAV_DEFAULT_BYTEPLUS_AUDIO_TRANSPORT = internal`. Le script d'archive TestFlight le remplace explicitement par `external` et vérifie la valeur dans l'archive. Ainsi, « dernier code » ne suffit pas à garantir « post-FX actif dans toute build ».

## 4. Graphe audio réellement relié au transport

```text
Microphone matériel
  → AVAudioEngine.inputNode
  → inputMixer
  → SimpleTune Superpowered (si activé, mode Simple)
  → inserts Audio Units ordonnés (EQ / compression / reverb ou chaîne Pro)
  → vocalMixer : gain et mute voix
       ├─→ vocalMonitorMixer → mix/limiteur monitoring → sortie locale
       └─→ finalMixer ← productionMixer ← AVAudioPlayerNode du morceau importé
              → limiteur de publication
              → tap Float32
              → PlacePerformanceAudioBus
              → conversion PCM16, 48 kHz, stéréo, 480 frames / 10 ms
              → BytePlus pushExternalAudioFrame
              → publication RTC
              → souscription distante autorisée
              → restitution BytePlus
```

Le moteur est créé dans `rebuildGraph` par `AVAudioEngine()`, capture par `inputNode`, puis démarre effectivement avec `engine.start()` ; ce n'est pas seulement un modèle de graphe. La session iOS est `.playAndRecord`, mode `.measurement`, avec fréquence demandée 48 kHz et buffer demandé 2,67 ms. Ce sont des valeurs demandées, pas une mesure de latence bout en bout. [PlaceAUv3VocalPluginHost.swift:762](https://github.com/sipiyou39/Meewav/blob/9907deed2998418574f80e10533aa5060fb802a7/Meewav/Features/Rooms/Services/PlaceAUv3VocalPluginHost.swift#L762) ; [PlaceAUv3VocalPluginHost.swift:994](https://github.com/sipiyou39/Meewav/blob/9907deed2998418574f80e10533aa5060fb802a7/Meewav/Features/Rooms/Services/PlaceAUv3VocalPluginHost.swift#L994) ; [PlaceAUv3VocalPluginHost.swift:1271](https://github.com/sipiyou39/Meewav/blob/9907deed2998418574f80e10533aa5060fb802a7/Meewav/Features/Rooms/Services/PlaceAUv3VocalPluginHost.swift#L1271).

La bifurcation monitoring/publication est explicite. Le tap public est sur le **limiteur après le mix**, pas sur le micro brut et pas sur la seule sortie casque. Le drainage public vers le mainMixer a un volume nul pour éviter la double écoute locale, sans supprimer le tap en amont. Désactiver le monitoring ne retire pas les effets du bus public. [PlaceAUv3VocalPluginHost.swift:1146](https://github.com/sipiyou39/Meewav/blob/9907deed2998418574f80e10533aa5060fb802a7/Meewav/Features/Rooms/Services/PlaceAUv3VocalPluginHost.swift#L1146) ; [PlaceAUv3VocalPluginHost.swift:1196](https://github.com/sipiyou39/Meewav/blob/9907deed2998418574f80e10533aa5060fb802a7/Meewav/Features/Rooms/Services/PlaceAUv3VocalPluginHost.swift#L1196) ; [PlaceAUv3VocalPluginHost.swift:1250](https://github.com/sipiyou39/Meewav/blob/9907deed2998418574f80e10533aa5060fb802a7/Meewav/Features/Rooms/Services/PlaceAUv3VocalPluginHost.swift#L1250).

## 8. Conclusion et arrêt

La référence à porter est démontrée : **contrôle de session Supabase + RTC BytePlus + graphe audio possédé par l'application + publication du bus traité**. Le choix ne résulte pas d'une dépendance installée ni du nom historique d'une colonne.

Il faut conserver les moteurs locaux Android existants et identifier leurs sorties/adaptateurs manquants. L'AutoTune vocal reste un traitement à porter, distinct de l'analyse BPM/gamme déjà portée. Les inserts iOS sont à inventorier par besoin réel ; leur simple nom dans le catalogue n'établit ni leur installation ni leur portabilité.

Les trois points à préserver lors d'une décision ultérieure sont la distinction démo/live, la séparation programme/cue privé et la distinction monitoring local/publication post-FX. L'entrée future iOS repose sur les mêmes contrats Rooms, identités et rôles ; cet audit n'en modifie aucun.

Vérifications effectuées : remote GitHub et branches, historique, références d'appel, construction du graphe, commandes UI/paramètres, bus et sender, réception, cycle de vie, puis sources Android. Pas de compilation iOS sous Windows, pas de test sur deux appareils, pas de capture visuelle, pas d'appel ni modification de backend pendant cette mission. **Audit terminé ; aucun câblage Android lancé après STOP.**
