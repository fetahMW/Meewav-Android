## Limite host Android observée

Le backend attribue à A le rôle `host` de B (`room.host_id` et `room_participants_v2.role`). L'écran Android A de cette Room LIVE a pourtant la classe `.is-viewer`, les onglets Chat/Mixeur/Wave, sans onglet Invités. Ce n'est pas une confusion du badge `HOST` des messages : le wrapper [`RoomViewer.tsx`](../../app/src/main/rooms-source/RoomViewer.tsx) pose `forceViewer` quand l'utilisateur réel correspond au `hostId` d'une Room LIVE, et [`usePlaceRoom.ts`](../../app/src/main/rooms-source/viewer-web/src/features/rooms/place/usePlaceRoom.ts) exclut explicitement le rôle host quand `forceViewer` vaut true. Le message envoyé depuis A a été persisté sous l'ID A ; le JWT exact de chaque requête n'a pas été capturé. La capture et le DOM du premier constat sont sous [`host-role-first-fail`](../../app/build/integration-run2/A/host-role-first-fail/). L'intention produit derrière ce forçage n'est pas documentée par ce test ; il rend ici impossible un test Android UI d'invitation/révocation host. Aucun correctif métier n'a été appliqué.

## Bugs cachés et limites révélées

1. **Limite produit à arbitrer : host LIVE rendu viewer sur Android.** Le `forceViewer` du wrapper neutralise les contrôles host malgré `rooms_v2.host_id=A` et `room_participants_v2.role=host`. La conséquence observée est l'absence du parcours Invités/révocation dans la Room B. Ce run ne démontre pas si le produit entend réserver ces actions à une autre surface.
2. **Défaut du flow de reprise, corrigé dans le harnais.** `launchApp` par défaut arrête l'app et détruit la task Rooms ; le flow historique est archivé en `.yaml.txt`. Le test valide utilise Home puis Recents sur la même task/PID.
3. **Fragilité B du harnais.** Perte initiale du service Activity récupérée par redémarrage ciblé sans wipe ; plus tard, bootstrap Maestro refusé faute d'espace. Les derniers gestes B ont été faits par ADB avec serial explicite et observés par CDP.
4. **Pas de contamination chat/état observée.** Mutation et fin de A n'ont changé ni backend B ni les deux expériences B. Les subscriptions/listeners et médias RTC internes restent non mesurables dans cet APK.

## Limites et nettoyage

Les pages WebView et ActivityRecords sont observables, les subscriptions JS/Realtime et tracks LiveKit internes ne disposent pas de compteur fiable dans cet APK. `Audio live déconnecté / Écouter le live` était visible sur B après le retour depuis Recents et encore avant la fin de Room, mais aucun flux RTC n'a été établi dans ce run : ce libellé n'est pas classé comme panne média. La gestion d'invité nécessite un parcours UI host absent sur ce client LIVE ; la révocation de rôle n'a pas été simulée par un RPC direct qui aurait court-circuité cette limite. Aucun correctif métier n'a été appliqué. Les deux UUID QA exacts ont été terminés et contrôlés `status=ended`, `participants_count=0` ; tous leurs participants ont un `left_at` non nul. Les messages QA restent dans ces Rooms terminées comme historique, sans suppression globale.
